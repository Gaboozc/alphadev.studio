## Protecting yourself from your own traffic

Earlier lessons in this area covered what to do when A PROVIDER rate-limits you (backoff with jitter on a 429). This is the reverse direction: protecting YOUR system and its downstream dependencies from load generated by your own traffic — a user spike, a buggy client retrying without control, a scraper.

## Rate limiting in your own API

Without an explicit limit, a single misbehaving (or malicious) client can burn through the entire model-call budget you share across all users. A per-user-identity limiter — not just by IP, which a legitimate user might share with others on a corporate network — is the first line of defense:

```python
from collections import defaultdict
import time

# Minimal example: per-user token bucket, in memory
# (in real production, this lives in Redis, not in a local dict)
buckets: dict[str, list[float]] = defaultdict(list)

def permitir(usuario_id: str, limite: int = 10, ventana_seg: int = 60) -> bool:
    ahora = time.time()
    peticiones = buckets[usuario_id]
    peticiones[:] = [t for t in peticiones if ahora - t < ventana_seg]
    if len(peticiones) >= limite:
        return False  # limit reached, reject or enqueue
    peticiones.append(ahora)
    return True
```

## Backpressure: what to do when more arrives than you can process

Rate limiting rejects outright. **Backpressure** is the alternative when flat rejection isn't acceptable — the system tells the caller to wait instead of failing. A queue with a max size fills that role: while there's room, it queues and processes in order; once full, only then does it start rejecting or returning an explicit "retry later" signal, instead of accepting work it will never be able to handle on time.

## Circuit breaker: stop trying when you already know something is broken

If a downstream dependency (the model provider, a database, another service) starts failing steadily, keeping on trying every individual request — even with backoff — slows every response and wastes resources on calls that are going to fail anyway. A circuit breaker counts recent failures and, once past a threshold, **stops trying** for a time window, returning an immediate error instead of waiting for a timeout on every request. Once that window passes, it lets one probe request through to see if the dependency recovered before reopening full flow.

## Which of the three you need

Rate limiting protects your system from EXCESS traffic, legitimate or not. Backpressure keeps you from accepting more work than you can process without silently failing. A circuit breaker stops you from hammering a dependency you already know is down. All three are complementary, not alternatives — a real production system almost always needs all three, applied at different layers.

## Tip

A rate limit without a clear error message to the user feels like the product "doesn't work," not like reasonable protection. Whenever you rate-limit, return an explicit response — status code 429 and a message saying when they can retry.

## Querying

```sql
SELECT nombre, precio FROM productos;

SELECT * FROM productos
WHERE precio > 100 AND stock > 0
ORDER BY precio DESC
LIMIT 20;
```

Filters used daily:

```sql
WHERE categoria IN ('laptops', 'monitores')
WHERE nombre ILIKE '%laptop%'          -- case-insensitive
WHERE proveedor_id IS NULL             -- NULL is compared with IS, never with =
WHERE creado_en >= now() - interval '30 days'
```

`NULL` isn't equal to anything, not even itself. `WHERE proveedor_id = NULL` never returns rows. It's one of the biggest time-wasting bugs.

### JOIN: combining tables

```sql
SELECT p.nombre, pr.nombre AS proveedor
FROM productos p
JOIN proveedores pr ON pr.id = p.proveedor_id;
```

`INNER JOIN` (or just `JOIN`) returns the rows that **match in both** tables. A product without a supplier won't show up.

`LEFT JOIN` returns **all rows from the left**, with nulls where there's no match:

```sql
SELECT p.nombre, pr.nombre AS proveedor
FROM productos p
LEFT JOIN proveedores pr ON pr.id = p.proveedor_id;
```

The mental rule: if you also need to see what has no match, `LEFT JOIN`. If you only care about paired rows, `JOIN`.

### Grouping and aggregating

```sql
SELECT
  pr.nombre AS proveedor,
  count(*) AS productos,
  round(avg(p.precio), 2) AS precio_medio,
  sum(p.stock) AS stock_total
FROM productos p
JOIN proveedores pr ON pr.id = p.proveedor_id
GROUP BY pr.nombre
HAVING count(*) > 3
ORDER BY productos DESC;
```

**`WHERE` filters rows before grouping; `HAVING` filters groups after.** Mixing them up is the classic mistake: you can't use `count(*)` in a `WHERE`.

### Writing

```sql
INSERT INTO productos (nombre, precio, proveedor_id)
VALUES ('Laptop 14', 1200.00, 3)
RETURNING id, creado_en;

UPDATE productos SET precio = 1150.00 WHERE id = 42;

DELETE FROM productos WHERE id = 42;
```

`RETURNING` gives you back the values generated by the database — the id, the timestamp — without a second query. It's specific to Postgres and very handy.

**Before every UPDATE or DELETE**, run the same `WHERE` with a `SELECT`. A `DELETE` without a `WHERE` wipes the entire table and there is no undo.

### Indexes

Without an index, searching by a column forces a scan of every row. With an index, the database goes straight there.

```sql
CREATE INDEX idx_productos_proveedor ON productos(proveedor_id);
```

What to index: **columns you filter by and foreign keys**. What not to: everything else. Every index speeds up reads and slows down writes, besides taking up space.

To check whether a query uses an index:

```sql
EXPLAIN ANALYZE SELECT * FROM productos WHERE proveedor_id = 3;
```

If you see `Seq Scan` on a large table, an index is missing.

### Transactions

When several operations must happen all-or-nothing:

```sql
BEGIN;
  UPDATE productos SET stock = stock - 1 WHERE id = 42;
  INSERT INTO movimientos (producto_id, tipo, cantidad) VALUES (42, 'salida', 1);
COMMIT;
```

If anything fails in between, `ROLLBACK` undoes everything. Without a transaction, you could subtract stock and fail to record the movement, and nobody would know why the numbers don't match.

## Tip

Get in the habit of first writing the SELECT with the WHERE you're going to use in an UPDATE or DELETE. Seeing the affected rows before modifying them turns a catastrophic mistake into a two-second scare.
